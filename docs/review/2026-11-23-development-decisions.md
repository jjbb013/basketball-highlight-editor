# 二次开发取舍 Review

日期：2026-11-23  
用途：记录开发中未暂停等待确认的问题、已采用的推荐方案和需要后续复核的边界。

## 决策记录

| 主题 | 已采用方案 | 理由与影响 | 状态 |
| --- | --- | --- | --- |
| 项目底座 | 在现有 Flutter、Python Engine 和 YOLO 篮球检测上增量开发，保留原分支历史 | 已有剪辑、审核、球员标签和 macOS 打包流程，重写会增加回归风险 | 已执行 |
| “创建识别模型”的含义 | 使用预训练 YOLO 检测/Pose，加本场持久化身份原型与可纠正归属模型 | 当前没有足够人工标注训练通用球员模型；不会虚构一个已训练模型 | 已执行，需真实素材校准 |
| 不依赖号码 | 综合发型、肤色、脸部区域、服装、鞋袜、体型和短时轨迹 | 业余比赛服装不统一；外观随遮挡和光线变化，所以保留置信度和复核 | 已执行 |
| 投篮人定义 | 找进球前最后一个有释放证据的触球者，而不是离篮筐最近的人 | 符合实际需求，可排除站在球路附近的无关人物 | 已执行 |
| 不确定结果 | 标记为推测/待复核，不自动变成确定标签 | 遮挡、多人重叠和球轨迹丢失时无法保证确定识别 | 已执行 |
| 命名传播 | 同场同身份的自动归属批量更新；人工纠正优先 | 满足命名一次标记所有进球，同时防止自动结果覆盖人工决定 | 已执行 |
| 跨天同人 | 导出阶段按规范化后的已命名球员聚合，不声称跨天 biometric 识别 | 换衣服、光线和场馆都会降低跨天外观匹配可靠性 | 已执行，可在项目选择时排除同名不同人 |
| 参考成片 | 12 人目录作为弱标签与回归参考；精确触球真值另行人工核验 | 成片名称能支持人物验证，但不自动证明剪辑前的最后触球帧 | 待本地验证 |
| 训练测试隔离 | 按完整成片/进球事件隔离，不把相邻帧随机分两边 | 避免同一事件泄漏造成虚高准确率 | 已执行 |
| 封面默认值 | 默认启用、3 秒，可关闭，0–10 秒可调 | 符合明确需求 | 已执行 |
| 封面样式 | 篮球场、海报、照片背景三种；标题/副标题/颜色/背景图可自定义 | 提供开箱样式，同时保留本地个性化 | 已执行 |
| BGM 默认值 | 默认启用、音量 20%，现场声不自动衰减，可关闭 | `amix` 不做整体归一化，避免现场声被意外减半 | 已执行 |
| BGM 来源 | 三类项目内原创可再分发循环音乐，不从参考成片提取；支持本地音乐 | 避免未知音乐版权；生成脚本和授权说明随源码保存 | 待制作与听感验证 |
| 后处理顺序 | 先剪辑/合并，再对最终输出加封面和 BGM | 防止合并视频为每个内部片段重复添加封面；沿用现有慢动作/HDR 逻辑 | 已执行 |
| 跨项目读取 | SQLite 只读，不改旧库、不复制原视频；启动时快照源校验信息 | 降低旧项目损坏和磁盘占用风险 | 已执行 |
| 失败与重试 | 临时文件、成品探测、原子发布、配置进 checkpoint | 增强失败保留原导出，避免重试叠加两次封面/BGM | 已执行 |
| macOS 构建 | 使用现有 GitHub Actions macOS runner 构建 arm64 和 x86_64 DMG | 本机没有完整 Xcode，不把本机命令行工具误当成完整构建环境 | 已执行 |
| 发布范围 | 推送功能分支和 macOS 预发布标签，不合并 main | 用户要求上传可下载版本，没有要求合并主干 | 已执行 |

## 需要重点 Review 的问题

1. 是否接受“同场高可靠聚类 + 跨项目按确认姓名聚合”作为第一版，而不追求未经验证的跨天自动识别？
2. 低置信度候选是否应默认不导出，还是保留导出但在 UI 标记？当前采用保留候选、明确待复核，沿用原项目“分析结果默认保留”的规则。
3. 是否长期采用项目内生成的三类 BGM；后续可替换为具有明确再分发授权的录音音乐。
4. 若有商业分发计划，需要复核 Ultralytics 的企业许可或整体开源义务与项目发布方式是否匹配。
5. 若希望 DMG 无 Gatekeeper 警告，需要后续提供 Apple Developer ID 签名与公证流程。

## 验证纪律

- 准确率必须来自隔离的人工真值评估，不能从模型自评分或参考文件名直接推断。
- 功能完成以实际测试、构建产物、Release 资产和安装校验为准，不以代码已写或工作流已启动为准。
- 本文件是决策记录，不是测试合格证明；实测结果另存本地验证报告。
